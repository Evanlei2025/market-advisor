### 架构一句话

```

  → 报告组装 (MD + HTML + latest.html)
  → build_compact → Server酱/企微 → 微信推送
```

5. **GitHub Actions 全自动链路**：从 cron 触发到报告生成→knowledge_base 回写→Pages 部署→微信推送。这是运营效率的基石，必须确保其稳定性。

6. **在途资金管理**：跟踪赎回确认/到账时间线，区分 settled_cash 和 pending_cash，避免重复买入。这是交易纪律的保障，需要确保跨日状态可靠持久。

## 设计边界（红线，不可逾越）

以下设计原则是用户明确要求的，执行任何改动时都必须遵守：

1. **不涉及个股**：这是用户**特意要求的设计边界**，不是功能缺失。系统聚焦公募基金和指数，不分析、不推荐、不跟踪任何个股。`llm.py` 中"不涉及个股"的约束必须保留。不要将"无个股覆盖"视为缺陷或待补功能。

2. **规则引擎优先**：`rules.py` 的输出是最终决策，AI 无权修改。不要让 LLM 输出直接参与买卖指令的生成。

3. **Gatekeeper 安全机制不可绕过**：三层审计必须保留，拦截>30% 自动回退 CRO 叙事的逻辑不可移除。修复数字审计的误拦截 ≠ 移除数字审计。

4. **动态止盈核心算法不可篡改**：T_eff = T_base × F_vol × F_hold × F_sector 的基本结构、clamp 和 T_cap 压缩、三档穿越检测、回撤保护，这些是算法资产，只能完善不能推翻。

5. **MIN-MERGE 最保守原则不变**：`equity_target` 中取所有触发规则的最小值，避免单一信号偏差导致过度配置。

6. **保持双轨降级能力**：LLM 不可用时降级为纯静态报告，数据源失败不阻塞整体运行。

7. **GitHub Actions 知识库回写机制不变**：`git add knowledge_base/` 自动 commit 回写 traces + recommendations 的跨日持久化机制必须保留并确保可靠。

8. **Python 3.12 兼容**：GitHub Actions 使用 Python 3.12，所有改动必须兼容。

9. **向后兼容 config.json**：新增配置项必须有默认值，确保旧版 config.json 不报错。

10. **本金规模无关**：当前持仓金额较小是测试阶段的正常现象，不是系统缺陷。不要因为金额小就降低对数据精度和逻辑严谨性的要求。

## 第一阶段：紧急缺陷修复（止血，最高优先级）

> 这一阶段修复 6 个直接导致功能故障的 bug。每个都是 Quick Win，预计 1-2 天完成。这些是"地基裂缝"，不修好无法往上盖楼。

### 1.1 修复 style.py 正则崩溃

**问题**：`style.py` 约第20行，`_spaceify` 函数使用 `re.sub` 的替换模板中包含 `\1 \2`，Python 将其解释为正则反向引用（group reference），当匹配文本中没有足够的分组时会抛出 `re.PatternError: invalid group reference 2`。此 bug 直接导致推送阶段崩溃（见 `logs/run.log` 约第185-198行）。

**修复方案**：
- 方案A（推荐）：使用 `re.sub` 的函数形式，在回调函数中手动拼接空格
- 方案B：确保替换字符串中的 `\1` `\2` 为字面量而非反向引用，或使用 `lambda m: m.group(1) + ' ' + m.group(2)` 形式
- 修复后用混合文本验证：`python -c "from style import _spaceify; print(_spaceify('沪深300今日下跌0.5%PE为12.3'))"`

**验收**：上述命令不报错且输出正确（中英数字间有空格）。

### 1.2 修复 Gatekeeper 数字审计误拦截产品代码

**问题**：`llm.py` 约第25行，`_NUM_RE = re.compile(r"\d+(?:\.\d+)?")` 会匹配所有数字序列。约第214-216行的数字审计逻辑遍历 AI 输出中的所有数字，检查是否存在于 `snapshot_data` 拼接字符串中。当 AI 写出"黄金Au99.99报904.92元"时，"99.99"被提取为数字并判定为越权数据引用，整句被删除。

**证据**：`logs/run.log` 约第269/275/280行，连续4次 `[GATEKEEPER] [拦截 数字审计:99.99] 黄金Au99.99报904.92元，趋势空头`。

**修复方案**：
1. 修改 `_NUM_RE` 正则为 `re.compile(r"(?<![A-Za-z])\d+(?:\.\d+)?")`，使用负向后行断言，排除前面紧邻字母的数字（即产品代码/品种代码中的数字不会被提取）
2. 同时在构建 `snapshot_data` 字符串时，确保所有产品代码（如"Au99.99"、"006195"）完整包含在内，使其内的数字能通过审计
3. 将拦截阈值从全局比例改为按板块分别计算（当前约第229行 `removed / len(sents) > 0.30` 是全局比例），一个板块的误拦截不应导致整篇回退

**验收**：
- AI 输出包含"Au99.99报904.92元"，snapshot_data 包含"Au99.99"和"904.92" → 不拦截
- AI 编造 snapshot 中不存在的数字（如"沪深300 PE为8.5"）→ 仍被正确拦截

## 第四阶段：AI 解读深度提升（可快速见效的产品差异化）

> 当前 AI 解读每板块仅 1-2 句模板化语言。这一阶段让 AI 输出真正有分析价值的内容。这是低成本的差异化，只需改 prompt 和上下文注入。

### 4.1 丰富 SYSTEM_PROMPT

**位置**：`llm.py` 约第37-98行的 `SYSTEM_PROMPT`。

**修复方案**：
1. **提高 max_tokens 至 5000-6000**（当前 3000 在多板块时易截断）
2. **在 SYSTEM_PROMPT 中增加以下分析维度要求**：
   - `market_logic_chain`（宏观逻辑链）：从当日宏观数据出发，构建"指标→行业→资产"的因果链（如"PMI 53.0 → 制造业扩张 → 周期类基金受益"）。注意不涉及个股，聚焦行业和指数层面。
   - `cross_market`（跨市场联动）：分析股债跷跷板、汇率-资本流动、商品-通胀预期等跨市场关系
   - `sector_tracking`（行业景气追踪）：基于上下游价差、库存周期分析行业景气度，聚焦基金重仓行业
3. **在 user_prompt 中注入更多上下文**：
   - 近5日指数趋势变化（涨跌幅序列）
   - PE 十年分位 vs 全历史分位的差异及原因分析
   - 组合与基准的对比
   - 昨日 recommendations.json 中的推荐项及今日表现（依赖第三阶段的回顾基础设施）
4. **调整 temperature**：保持 0.4 或微调至 0.35，确保分析稳定

### 4.2 丰富产品解读模板

**当前问题**：产品解读模板化（"近1年收益X%，回撤Y%，费用Z%"）。

**修复方案**：
1. 在 SYSTEM_PROMPT 的产品解读部分，要求每个产品解读包含：
   - **业绩归因**：近期收益主要来自哪个因子（行业配置/选股/择时/转债）
   - **风格分析**：大盘/小盘、价值/成长、行业集中度
   - **同类对比**：与同类基金排名差异及原因
   - **具体风险点**：如"重仓周期行业，若经济下行则..."，而非泛泛的"波动风险"
2. 在 user_prompt 中注入产品的持仓数据（top10 重仓股/行业配置）和同类基金对比数据

### 4.3 Gatekeeper 阈值优化

**修复方案**：将拦截阈值从全局比例改为按板块分别计算。当前约第229行 `removed / len(sents) > 0.30` 是全局比例。改为每个板块独立计算 `removed / len(section_sents) > 0.30`，只回退该板块，避免一个板块的误拦截导致整篇回退。

## 第五阶段：投资逻辑完善（底层功能，高标准）

> 底层投资逻辑的严谨性直接影响每一条信号的可靠性，必须追求高标准。

### 5.1 添加组合基准对比

**位置**：`rules.py` 约第668-694行的 `portfolio_diagnostics`。

**当前问题**：计算了波动率/最大回撤/VaR95，但无基准对比，用户无法知道是否跑赢大盘。

**修复方案**：
1. 获取沪深300指数近250日收益率序列（DataFetcher 已有指数数据）
2. 获取中证全债指数近250日收益率序列
3. 计算 alpha（超额收益）、beta（市场敏感度）、信息比率（alpha/跟踪误差）
4. 按资产配置比例构建复合基准（如 60%沪深300 + 40%中证全债）
5. 在报告中「组合诊断」板块增加：`vs 沪深300: 超额收益 +X.X%（alpha=X.XX, beta=X.XX）`
6. 可复用已有的 `returns_map` 数据

### 5.2 改进买入候选排序逻辑

**位置**：`rules.py` 约第418-579行 `build_order_book`。

**当前问题**：买入候选排序简单（仅按"是否已持有"和"代码"排序），无质量评分。

**修复方案**：
1. 添加 `score_candidate(product_ctx)` 函数，综合评分：
   - 夏普比率（年化收益/年化波动率）：权重 40%
   - 最大回撤：权重 20%（回撤越小越好）
   - 费率（管理费+赎回费）：权重 15%
   - 规模适度性：权重 10%（太小有清盘风险）
   - 同类排名百分位：权重 10%
2. 在 `build_order_book` 的买入候选排序中，按 `score_candidate` 降序排列

### 5.3 扩展权益目标的多指数覆盖

**位置**：`rules.py` 约第33-77行 `equity_target`。

**当前问题**：PE 阶梯仅基于沪深300和中证500，缺少创业板指等估值信号。

**修复方案**：
1. 在 `equity_target` 中增加创业板指 PE 分位判断
2. 当创业板指 PE 分位≥90%时，额外触发权益目标下调（如 -5%）
3. 在 MIN-MERGE 逻辑中纳入更多指数的信号
4. 保持最保守原则不变

### 5.4 EP 安全阀利率适配

**位置**：`rules.py` `equity_target` 中的 EP 安全阀。

**当前问题**：EP 安全阀阈值 10% 为硬编码，未考虑利率环境。当前 10 年国债 1.71% 处于历史极低位，EP 天然偏高。

**修复方案**：
1. 将 EP 安全阀阈值改为动态：基于 10 年国债收益率的十年分位调整
2. 国债收益率处于历史低位（<20%分位）时，EP 安全阀阈值适度上调至 15%
3. 国债收益率处于历史高位（>80%分位）时，EP 安全阀阈值下调至 5%

### 5.5 动态止盈算法边界条件完善

**位置**：`rules.py` 约第173-382行。

**当前问题**：
- 回撤保护条件 `st["r_hold"] > 0` 排除了从大幅盈利直接变为亏损的场景
- tier_gap 固定值 [0.05, 0.10]，未根据波动率动态调整

**修复方案**：
1. 回撤保护：考虑放宽条件，当从峰值回撤超过 dd_thr 时即使当前亏损也应触发保护性信号（当前 `r_hold > 0` 的限制可能遗漏"从大赚到大亏"的快速变脸场景）
2. tier_gap 动态化：高波动产品档位间距应更大（避免频繁触发），低波动产品可更紧凑。可基于年化波动率分位调整 tier_gap
3. 确保 `test_tp.py` 覆盖新增的边界条件，每个改动都新增对应测试用例

### 5.6 强化规则引擎的输入校验

**修复方案**：
1. 在 `rules.py` 的每个公开函数入口处添加输入校验：NaN 防护（已有部分）、None 防护、类型检查、数值范围检查
2. 当输入数据异常时，返回安全的默认值（如权益目标返回0%，止盈信号返回不触发）而非抛异常
3. 添加 `rules.validate_config(config)` 函数，在系统启动时校验配置完整性

## 执行建议

1. **严格按阶段顺序执行**：先止血（第一阶段），再稳基座（第二阶段），再搭学习地基（第三阶段），然后提升内容质量（第四阶段），完善投资逻辑（第五阶段），最后优化体验（第六阶段）。

2. **每阶段完成后运行验证**：`python main.py` 确认完整流程不报错，检查 `logs/run.log` 无 ERROR 级别日志。

3. **测试优先**：`test_tp.py` 已有 13 个止盈算法场景测试。改动 `rules.py` 后必须运行 `python test_tp.py` 确认全部通过。新增功能应同步新增测试用例。

4. **保持最小改动原则**：遇到不确定的设计决策时，优先保持现有架构不变，做最小改动。宁可保守也不要破坏已有功能。

5. **每阶段提交一次**：保持 commit 粒度适中，便于回滚。

6. **底层功能高标准，经验积累功能保运转**：对数据采集、规则引擎、状态持久化、错误处理等底层功能追求极高的健壮性和完整性。对止盈算法胜率、信号命中率等需要长期数据积累的指标，当下只需确保数据采集和留痕机制运作良好，不苛求数据量和统计结果。

7. **关注 knowledge_base/ 回写的可靠性**：这是云端唯一的跨日持久化通道，是系统"自我学习"的物理基础。每次改动后都要确认 GitHub Actions 的 `git add knowledge_base/ && git commit` 步骤正常执行，traces.json 和 recommendations.json 跨日可见。
